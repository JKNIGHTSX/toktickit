## 3. Reflection

### 3.1. What Made the Prompts Effective

The most effective Lab 4 prompts combined **data security invariants** with **database mechanics**. For example, framing the Requester Dashboard prompt as "derive ALL data from `req.session.userId` — Requester A cannot access Requester B's data even if they guess the ID" immediately surfaced the need for a dedicated isolation test rather than just a happy-path test. Similarly, framing the resolution gate as "this must fire server-side, not client-side only" immediately guided the implementation to validate at the API layer before any client-side button state.

The pattern of asking the AI to "describe what must NOT happen" remained the most reliable technique for security-critical features across all four labs.

### 3.2. Corrections and Adjustments

Several corrections were necessary during development:

1. **ActionTaken Performer Schema**: The initial schema used a text field `performerName` instead of a foreign key relation to `User`. I corrected this to a proper relational `performedById` field so that performer identity is enforced at the database constraint level and cannot be faked. This change also enabled the `performedBy { name, email, role }` JOIN in the API response without additional queries.

2. **Resolution Gate DB Query**: The initial two-query approach (COUNT actions, then update if count > 0) created a potential TOCTOU (time-of-check/time-of-use) window. I consolidated this into a single Prisma fetch with `_count` on the `actions` relation, eliminating the race condition and reducing round-trips.

3. **Dashboard Default View & mustChangePassword**: The initial login flow unconditionally set the default view to `Dashboard`, bypassing the `mustChangePassword` intercept from Lab 3. I corrected this by reading `user.mustChangePassword` from the `checkAuth` response before determining the initial view.

4. **Navigation Filtering Regression**: Adding dashboard drill-down navigation broke the existing status filtering behavior in `StaffTicketQueue` — clicking "Status: New" on the dashboard card showed all tickets because no filter state was forwarded. I fixed this by extending the view state to carry a `staffQueueFilter` parameter.

5. **Testing Library `getByRole("button")` Conflict**: When a card container div had `role="button"` and an inner `<button>` with the same accessible name, `getByRole("button", { name: /status: new/i })` returned multiple elements. Fixed by removing `role="button"` from the wrapper div, relying on the semantic inner button for role queries.

### 3.3. Key Takeaway

Lab 4 reinforced that **audit integrity** in multi-role systems requires careful separation of *who performed an action* from *who owns the resource*. The Actions Taken `performedById` field being independent from `Ticket.ownerId` is a small schema decision with large correctness implications: it enables any authorized staff member to contribute actions without changing ticket ownership, and it ensures the audit log accurately reflects the person who performed physical or technical work.

The concurrency challenge also highlighted an important lesson: optimistic concurrency control is most effective when the client preserves all entered form data on conflict, allowing the user to reload the latest server state and retry with their changes still visible. This UX detail is as important as the HTTP 409 status code itself.
